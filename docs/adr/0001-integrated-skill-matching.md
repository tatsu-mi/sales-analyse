# ADR-0001: 統合スキル情報による案件照合と個人別の機械判定

- 日付: 2026-10-22
- 状態: 採用
- 更新: 抽出対象・原文引用・必須条件のAI出力形式は [ADR-0002](0002-keyword-only-extraction.md) により変更。
- 実装状況: 実装済み。オフラインテストで検証し、実データでの精度・トークン量の比較は未実施。

## 背景

変更前の個人別マッチングは、同じ案件情報を各人のプロフィールとともにAIへ渡し、必須条件や勤務条件を照合していた。案件情報の送信と解釈を人数分繰り返すため、人数・案件数の増加に伴ってトークン消費が増える。

全員のスキルをキーワード単位に統合し、各キーワードに複数のキャリアシートIDを紐づければ、案件の意味を解釈する処理を共通化できる。一方、キーワードだけでは経験年数、担当業務、役割、実務区分などの関係が失われ、必須条件を誤って充足と判定するおそれがある。

そこで、共通照合に使う統合キーワードと、条件判定に使う個人別の経験詳細を両方保持する。

## 決定

AIは情報の構造化・表記の正規化・案件と統合キーワードの照合に使用する。個人別の候補抽出、全必須条件の判定、得点計算、Top10作成はプログラムで行う。

案件は統合キーワードに対して一巡で照合し、個人ごとのAI照合を行わない。「一巡」は単一のAPI呼び出しを意味せず、入力・出力上限に応じた分割や失敗時の再試行を許容する。

### 処理フロー

1. キャリアシートから個人別の経験詳細・勤務条件を抽出する。
2. 全員分のスキルを統合キーワードに整理し、個人への紐づけを作る。
3. 案件から全必須条件・歓迎条件を抽出する。
4. 案件の各要件と統合キーワードを照合する。
5. 一致キーワードから個人別の候補案件を抽出する。
6. 候補案件の全必須条件を、個人別の経験詳細・勤務条件と比較する。
7. 必須条件を充足した案件の得点を計算する。
8. 個人別に合計点数順のTop10を作成する。未確認候補と除外理由は別途保持する。

募集終了、期限切れ、共通の除外条件を反映する。共通のTop10などで先に候補を制限せず、個人別の条件判定後にTop10へ絞り込む。

## 保持する情報

### 個人別の経験詳細

キャリアシートには、表示名や並び順から独立した固定IDを付与する。

| 情報 | 内容 |
| --- | --- |
| キャリアシートID | 個人を識別する固定ID |
| スキル | 技術、担当工程、業務知識、ヒューマンスキル |
| 経験区分 | 実務／実務以外／未確認 |
| 経験期間 | 開始・終了時期、明記された経験月数、算定根拠 |
| 経験の関係 | どの業務で、どの技術を、どの役割で使ったか |
| 勤務条件 | 稼働開始日、勤務地・通勤条件、希望単価など |
| 根拠 | 元資料の該当記載と参照先 |
| 更新情報 | 元資料の変更検出情報、抽出ルールの版 |

例えば「Java開発のメンバー経験」と「別業務でのPython開発のリーダー経験」を持つ人について、Javaでのリーダー経験があるとは判定しない。

同時並行の期間を経験年数へ重複加算しない。業務全期間を無条件に各スキルの経験期間とみなさない。期間を確定できない場合は、推測で補完せず未確認情報として保持する。

スキルの登録・加点には経験年数の下限を設けない。年数は、案件側が必須としている場合の条件判定に使用する。

ヒューマンスキルも元資料の記載・経験に基づいて抽出する。過去のマッチングフィードバックを、その人の経験を示す根拠として扱わない。

### 統合キーワードと個人への紐づけ

統合キーワードには固定ID、名称、必要な意味の説明を持たせる。表記揺れ・同義語は統一するが、意味が異なるスキルは分ける。

例:

```text
キーワードID: skill_java
名称: Java
紐づけ:
  キャリアシートA → 実務、経験詳細A-1
  キャリアシートB → 実務、経験詳細B-2
  キャリアシートC → 実務以外、経験詳細C-1
```

「JavaとJavaScript」「顧客折衝と一般的なコミュニケーション能力」は同一視しない。

案件照合時にAIへ渡す情報は、主に統合キーワードのID・名称・意味の説明とする。キャリアシートIDとの対応表や個人の経験詳細はプログラム側で保持し、照合のたびに送信しない。

### 案件の条件

| 情報 | 内容 |
| --- | --- |
| 案件ID・要件ID | 案件と各要件を識別するID |
| 必須／歓迎 | 条件の位置づけ |
| 対象 | スキル、工程、役割、勤務条件など |
| 比較条件 | 実務の要否、最低経験期間、日付や金額など |
| 経験の関係 | 特定技術を使った業務での特定の役割など |
| 論理条件 | AND／ORとそのまとまり |
| 根拠 | 案件原文の該当記載 |
| 判定可能性 | 機械判定可能／要確認 |
| 抽出状態 | 原文省略、未処理の条件、抽出失敗など |

必須条件は統合キーワードの有無に関係なく全件抽出する。例えば誰にも英語の登録がなくても、「英語での顧客折衝必須」を削除しない。

曖昧な条件や機械判定できない条件は要確認として保持する。抽出結果が空であることを、必須条件が存在しない証拠として扱わない。

### 案件とキーワードの照合結果

案件ID、要件ID、キーワードIDの対応表を保持する。要件の種類・原文の根拠・条件式は最初のメール分析結果に保存し、照合結果から参照する。照合AIの応答はIDの対応表だけとする。

この照合結果は関連案件の抽出と加点に使用する。類似性だけで必須条件を充足と判定しない。例えばAWS経験はクラウド案件との関連性を示しても、Azure実務必須を満たす根拠にはならない。

重みは、必須／歓迎や要件の種類などの共通ルールからプログラムで決定する。AIが案件ごとに自由な点数を付ける方式は採用しない。

## 必須条件の機械判定

個人に紐づいた候補案件について、一致した条件だけでなく、その案件の全必須条件を確認する。判定には個人別の経験詳細を参照する。

| 判定 | 意味 | 扱い |
| --- | --- | --- |
| 充足 | 全必須条件を根拠付きで確認できる | 得点計算・Top10の対象 |
| 不足 | 必須条件を満たさないことが確認できる | 対象から除外 |
| 未確認 | 不足は確定していないが、充足を確認できない | 通常のTop10から外し、要確認候補として保持 |

論理条件は次の3状態で評価する。

- AND: いずれかが不足なら不足、全て充足なら充足、それ以外は未確認。
- OR: いずれかが充足なら充足、全て不足なら不足、それ以外は未確認。

以下のルールを適用する。

- 記載がない経験を未経験とは断定しない。
- 同一スキルや明示的に定義した充足関係で比較し、意味が近いだけの一致を充足に使わない。
- 異なる業務の技術・役割を組み合わせて、存在しない経験を作らない。
- 比較対象や期間、条件の解釈が不明な場合は未確認とする。
- 機械判定に対応できない条件を読み飛ばして充足にしない。
- 原文の省略、抽出漏れ、検証できない根拠がある場合は、全条件の充足を断定しない。
- 過去の稼働開始予定を、そのまま現在の稼働可否の根拠にしない。

通勤時間は経路・所要時間などのデータが必要であり、地名だけから推測しない。既存の「片道90分以内、または出社不要のフルリモート」という条件を反映し、判断材料がなければ未確認とする。初日・研修時のみを含め出社が必要な場合は、出社条件を確認する。フルリモートでも明示された居住地制限などは確認する。

AIを使わないのは比較・判定処理であり、判断材料が欠けていても自動的に合否を確定できるという意味ではない。

## 得点計算とランキング

必須条件を充足した案件について、一致したスキルの重みを合計する。実務以外の経験の得点は、実務の10分の1とする。

```text
個人の案件スコア = 各案件要件について算出した得点の合計

経験区分の係数:
  実務     = 1.0
  実務以外 = 0.1
  未確認   = 加点保留
```

得点はキーワードの出現数ではなく、案件の要件単位で管理する。

- 要件ごとに加点上限を設け、同義語の重複一致で多重加点しない。
- OR条件で複数の選択肢に一致しても、要件の上限を超えて加点しない。
- 同じ対象に実務・独学の両方がある場合は実務分を採用し、二重加点しない。
- 複数の業務で同じスキルを使っていても、経験件数分の加点はしない。
- 得点と必須条件の合否を独立させる。実務以外の加点で実務必須条件を通過させない。

合計点数の降順で個人別Top10を作成する。対象が10件未満なら該当件数を出力し、未確認・不足の案件で埋めない。同点時の並び順は固定する。

要件数が多い案件ほど合計点が高くなりやすい性質は残る。実データで偏りを確認し、必要に応じて配点を調整する。具体的な配点・要件上限・同点時の順序は、実装時に設定とルールとして明文化する。

## 出力と追跡可能性

| 出力 | 内容 |
| --- | --- |
| 個人別Top10 | 必須条件を充足した案件を合計点数順に表示 |
| 得点の内訳 | 加点対象の要件・キーワード・経験区分・得点 |
| 必須条件の判定記録 | 各条件の判定、個人の経験詳細、原文の根拠 |
| 要確認候補 | 未確認条件と必要な確認事項 |
| 除外記録 | 不足した条件と判定根拠 |

元資料の引用根拠を検証し、別人の経験やマッチングフィードバックを経験の証拠として混入させない。引用の存在確認だけでは意味の解釈の正しさまでは保証できないため、抽出精度も評価対象にする。

## 再利用と更新

| 変更 | 再処理 |
| --- | --- |
| キャリアシート更新 | 該当者の情報抽出・紐づけ更新・個人別再計算 |
| 案件更新 | 該当案件の条件抽出・キーワード照合・個人別再計算 |
| 配点変更 | AIを使わず得点を再計算 |
| キーワード追加 | 既存案件との照合を補完し、関連する個人の結果を再計算 |
| キーワードの意味・抽出・正規化ルール変更 | 影響する抽出結果・照合結果を無効化し、再生成 |
| 個人の削除 | 紐づけと個人別出力を更新 |

元資料、統合キーワード、抽出・照合・判定・配点ルールの変更を識別できるようにし、古い結果を誤って再利用しない。新しいキーワードを持つ人が追加された場合は、既存案件との未照合を残さない。

## 効果と制約

- 同じ案件を人数分AIへ渡す処理をなくし、トークン消費の削減を見込む。
- 個人別の得点・合否・除外理由を、保存した情報から再現できる。
- 人数が増えた際の追加処理は、主に個人情報の初回抽出とプログラムによる比較・集計になる。ただし、新規キーワードが増えた場合は照合の補完が必要になる。
- 全員共通の抽出・正規化・照合の誤りは複数人に影響するため、根拠の保持と検証が必要になる。
- 情報不足の案件・プロフィールでは未確認が増え、Top10が埋まらない場合がある。
- 統合辞書の大きさ、出力量、分割回数、再試行などにも消費量が左右されるため、削減率を人数比だけで断定しない。

## 検討した代替案

| 案 | 判断 |
| --- | --- |
| 現行の個人別AI照合を継続する | 個人の文脈を扱いやすいが、案件の送信・解釈を人数分繰り返すため採用しない |
| 全員のキャリアシート全文をまとめて案件と照合する | 入力・出力が大きくなり、個人情報の混同も検証しにくいため採用しない |
| 統合キーワードの一致点だけでTop10を作る | 経験の関係や必須条件を確認できないため採用しない |
| 統合キーワード照合と個人別の機械判定を組み合わせる | 共通照合による削減と個人の条件確認を両立できるため採用する |

## 検証方針

同じ人材・案件データと人が確認した期待結果を使用し、現行方式との差分を評価する。

- 必須条件を満たさない案件の誤通過。
- 関連案件の取りこぼしと個人別Top10の妥当性。
- 未確認率と、未確認になった理由。
- AIの入力・出力トークン数、呼び出し回数、再利用の効果。
- 別業務の技術と役割の混同、期間の二重加算、同義語の二重加点がないこと。
- 一致しなかった必須条件も判定対象に残ること。
- AND／OR、実務必須、実務以外の0.1倍、根拠不明の扱い。
- キーワード追加・案件更新・個人情報更新後に結果が正しく更新されること。

## 実装時に確定したルール

### 2026-10-23: 最初のメール分析で構造化を完了し、後段の本文再送を廃止

初期実装では、最初のメール分析で必須条件を文章として抽出した後、案件照合時に元本文と抽出済み情報を再送し、条件式の作成と抽出漏れ確認を行っていた。本文の読解と漏れ確認が重複し、トークン削減の意図に反していたため、次の責務に変更する。

| 工程 | AIの処理 | 保存・送信する情報 |
| --- | --- | --- |
| 最初のメール分析 | 案件抽出、全必須条件の構造化、原文による漏れ確認、歓迎・関連条件と通勤条件の抽出 | `mandatory_requirements` の各項目に `root`・`nodes` を保存し、`matching` に歓迎条件・通勤条件・抽出状態を保存 |
| 統合キーワード照合 | 構造化済み要件と辞書の対応付けのみ | 案件ID、要件ID、短い要件説明、スキル名と統合辞書を送信。応答は要件IDとキーワードIDの対応表のみ |
| 個人別の条件判定・得点計算 | AIを使用しない | 保存済みの条件式へ対応表を結合し、個人の経験詳細と比較 |

元本文、監査用の原文引用、条件式のノード、個人情報をキーワード照合へ送信しない。後段での条件追加・条件式の再生成も行わない。根拠の引用と構造化結果は最初の分析時に検証し、ローカルの保存情報として追跡可能にする。

`keyword_matches.json` には軽量な対応表を保存し、`project_matching.json` にはプログラムで結合した条件式・対応表・抽出状態を保存する。

パイプライン版を6へ変更し、旧形式の案件抽出・照合キャッシュは流用しない。v5からのresume移行は追加せず、新規実行を前提とする。同一版の通常の再開処理は維持する。キャリアシート抽出の形式・指示文は変更していないため、既存の検証済みキャッシュは再利用できる。

### 判定形式

必須条件は、ルートIDとノード一覧からなる式で保存する。`all`（AND）、`any`（OR）、`atom`（比較可能な条件）、`unknown`（機械判定不能）を扱う。式の循環、未参照ノード、条件の欠落、不正な参照を検証する。

| 比較対象 | 対応する判定 |
| --- | --- |
| スキル・工程・役割等 | 同じ経験内での対象の存在、実務区分、最低経験月数 |
| 稼働開始日 | 案件開始日までに稼働開始可能か。過去の予定日は未確認 |
| 希望最低月額 | 円単位の案件月額上限以下か。単位が不明なら未確認 |
| 居住地・契約種別 | 正規化後の同一値か。複雑な条件は未確認 |
| 通勤 | 全出社先への片道90分以内、または出社不要のフルリモート |
| その他・曖昧な条件 | 未確認として保持 |

年月から経験期間を算定する場合、重複を除き、分析基準月の前月までを計上する。日付不明の業務期間は複数件を合算せず、単一期間の下限として扱う。最低年数未達を不足とするには、対象の総経験月数の明記など、不足を確定できる根拠を必要とする。

通勤判定にはプロフィール内で確認できる経路を使用し、経路検索サービスは追加していない。90分以外の制限や出社頻度の希望など、対応していない勤務条件は未確認とする。

### 配点と順序

`config.toml` の `[analysis]` に次の正の整数を設定する。省略時にも同じ値を使用する。

| 設定 | 初期値・要件ごとの加点上限 |
| --- | --- |
| `matching_mandatory_weight` | 10 |
| `matching_welcome_weight` | 5 |
| `matching_related_weight` | 2 |

各要件の基準点を列挙された対象項目数で等分し、一致した項目ごとに経験係数（実務1、実務以外0.1、不明0）を掛けて合算する。分母にはキャリアシートの辞書に存在しない対象も含め、正規化で同義と判定した語は1項目と数える。例えば7項目を列挙した必須要件（基準点10点）で実務経験が1項目だけ一致する場合は10÷7点となる。ANDで結合したスキル条件では必要な経験のうち低い係数を上限とし、ORでは充足する選択肢の経験係数を上限とする。同じ意味の必須条件や、必須条件・歓迎条件・関連条件間で同じキーワードが重複する場合の加点を抑止する。重複を除外しても元の対象項目数は減らさない。

得点は内部的に分数で合計し、0.1点単位への丸めは行わない。レポートには該当数/対象数も表示する。同点時は、募集中の明記、受信日時、UID、案件キーの降順で並べる。同一メールの複数案件はその人にとって最上位の案件で代表する。表示件数は既存のルール設定に従い、最大10件とする。

### 保存と再利用

- `career_facts.json`: 個人別の経験詳細・勤務条件と抽出状態。
- `integrated_skills.json`: 統合キーワードとキャリアシートIDへの紐づけ。
- `project_matching.json`: 案件ごとの全必須条件の式、キーワード照合結果、抽出状態。
- `engineer_assessments.json`: 候補案件の個人別判定・得点・除外理由の記録。
- `ranked_emails.json`: 個人別Top10と要確認候補。

キャリアシートIDは見出しの `｜` 以降の資料識別子から生成する。区切りがない場合は名前を使用するため、名前変更時も同一IDを維持するには資料識別子を固定する。

AIへの入力内容、モデル・出力設定、スキーマ・指示文、パイプライン版をキーとして、検証済みレコードを個別に再利用する。配点変更・個人の追加順序は案件照合のキーに含めない。統合辞書が変わった場合は、取りこぼしを避けるため既存案件も再照合する。

ローカルでは `.analysis_cache/token-files-v1` に保存する。SharePoint定期実行では `run-state/matching-cache.zip` に検証済みの個人情報・案件照合レコードを保存し、新規実行にも引き継ぐ。読み込み時は現在の資料とルールで再検証する。失敗時の仮レコードは再利用対象にしない。

抽出失敗や未処理情報は要確認として残す。API接続・認証エラーや、単一資料・指示文だけで入力上限を超える場合は停止し、再開可能な状態を保存する。

仕様・設計の記録先は本ADRとし、README.mdはセットアップ・実行手順・設定方法などの利用案内に限定する。
